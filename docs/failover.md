# Автопереключение (Failover)

Пошаговый разбор с командами для проверки на сервере: [autoswitch-howto.html](autoswitch-howto.html).
Здесь — краткая справка.

Пулы серверов **AmneziaWG 2.0**: при отказе одного узла клиент продолжает работать через
другой без ручных действий на устройстве. Раздел меню: **Автопереключение**. Только
для нативного AmneziaWG 2.0 — OpenVPN и WireGuard/AmneziaWG 1.5 сюда не входят.

## Два режима

**«На фронт-сервере» (`dnat_front`) — рекомендуется.** У клиента один статический
конфиг, который никогда не меняется. Какой сервер реально отвечает — решает панель
через выделенный узел-фронт: фронт держит DNAT-правило на текущий активный узел пула,
переключение происходит на сервере, клиенту делать ничего не нужно. Работает со
штатным приложением AmneziaWG (Android, Windows, роутер).

**«На устройстве» (`client_sync`)** — когда фронта нет: клиенту нужно отдельное
приложение (например [panel_auto_reverce](https://github.com/shax0491/panel_auto_reverce)),
которое само хранит несколько конфигов и переключается по своему пингу.

## Как настроить пул `dnat_front`

1. **Фронт-узел** — любой узел типа «Прокси» с установленным `proxy_agent`. Начиная с
   версии, где `proxy_agent` ставится автоматически вместе с `node_agent`
   (см. [proxy-agent.md](proxy-agent.md)), **любой существующий VPN-узел уже готов быть
   фронтом** — отдельный сервер заводить не обязательно.

   **Важно: фронт должен быть узлом, НЕ входящим в этот же пул.** Фронт держит
   единственное DNAT-правило, на которое смотрит клиент, — если фронт совпадает с
   одним из участников пула (например, резервным), смерть именно этого узла обрушит
   весь пул целиком, точно так же, как смерть основного: переключаться в этот момент
   попросту некому. Рекомендуемый вариант — сама панель (она и так должна быть всегда
   доступна для управления): поставьте на неё `proxy_agent` тем же
   `install.sh --proxy-only --with-systemd -y`, заведите как узел типа «Прокси» и
   назначьте фронтом обоих пулов (на разных UDP-портах, раз IP один). Для публичного
   адреса клиента используйте отдельную A-запись, не совпадающую с публичным именем
   самой панели (например `de3.hoststatus2346.ru`, если панель ещё и на `panelaz...`).
2. Создайте пул, выберите стратегию «На фронт-сервере», добавьте минимум 2 узла-участника
   (первый по приоритету — основной, источник identity).
3. Назначьте фронт (узел + UDP-порт AmneziaWG 2.0, обычно тот же порт, что слушает AWG2 —
   по умолчанию `53443`).
4. Для каждого узла, кроме основного, нажмите **«Клонировать identity»** — без этого
   переключение на такой узел откажет: у него не будет ни серверного ключа, ни клиентских
   профилей, совпадающих с основным.
5. Раздайте клиенту конфиг — панель сама пишет `Endpoint` = адрес **фронта** во все
   клиентские файлы пула (и на основном узле, и на всех склонированных резервных) при
   назначении/смене фронта и при каждом клонировании identity, так что скачанный с
   «Клиенты» конфиг уже правильный без ручной правки.

### Пример: фронт на самой панели для нескольких пулов (без ручных правок в базе)

Полностью через SSH-консоль панели + веб-интерфейс, ничего вручную в БД:

1. На сервере панели (там же, где `/opt/AdminPanelAZ`):
   ```bash
   cd /opt/AdminPanelAZ
   sudo ./install.sh --proxy-only --with-systemd -y
   ```
   В конце вывода будет `PROXY_AGENT_API_KEY` — скопируйте его, он больше нигде не
   показывается (только пересоздать ключом заново, если потеряли).
2. **Настройки → Модули** — включите «Прокси-узлы», если ещё выключено.
3. **Узлы → Добавить узел** → тип «Прокси»: хост — публичное имя панели (лучше
   отдельная A-запись, а не та, что открыта в адресной строке админки — см. ниже),
   порт `9101`, ключ — из шага 1.
4. Для отдельного публичного имени (не обязательно, но чище): заведите у вашего
   DNS-провайдера ещё одну A-запись на тот же IP, что и панель (например
   `vpn-front.example.com → <IP панели>`), и используйте её как хост узла на шаге 3
   вместо основного домена панели.
5. **Автопереключение** → откройте пул → **Назначить фронт** → выберите только что
   добавленный узел, порт — любой свободный UDP-порт на этом хосте (например `53443`).
   Для второго пула на **том же** фронт-узле обязательно возьмите **другой** порт
   (`53444` и т.д.) — один хост, один порт = одно DNAT-правило, разные пулы не могут
   делить порт.
6. Готово — панель сама переписывает `Endpoint` в клиентских конфигах на адрес фронта
   при назначении и при каждом клонировании identity (см. шаг 5 выше). Отдайте клиенту
   свежий конфиг с «Клиенты», в нём уже правильный адрес.

## Identity — самое важное

AmneziaWG 2.0 требует **побайтового совпадения** параметров обфускации
(`Jc/Jmin/Jmax/S1-S4/H1-H4`) и серверного ключа между клиентским конфигом и живым
интерфейсом сервера — иначе хендшейк не проходит. «Клонировать identity» копирует
серверный ключ и **весь** список клиентских профилей с основного узла на резервный,
перезаписывая то, что было на резервном раньше. Поэтому:

- Резервный узел должен быть **выделен под этот пул** — не используйте для этого узел
  с собственной независимой базой клиентов, которую нельзя перезаписывать.
- После первого клонирования резерв надо **обновлять** каждый раз, когда меняется список
  клиентов пула (кнопка «Обновить» у той же карточки участника).

### Конфликт подсетей на резервном узле — типовая причина «хендшейк есть, трафика нет»

Если на резервном узле уже стоял **другой** WireGuard-совместимый VPN на той же
подсети (например старая установка AmneziaWG 1.5 до `setup.sh` этого форка), в
таблице маршрутов ядра окажутся два одинаковых по длине маршрута на один `/24` —
и обратный трафик клиентов AWG2.0 может молча теряться, хотя хендшейк проходит
(это отдельный UDP-обмен, маршрутов не касается). `setup.sh`/`client.sh` сами
защищаются от этого (добавляют точные `/32`-маршруты на каждого пира — see
`setup/root/antizapret/awg2-fix-routes.sh` в основном репозитории), но если резерв
собирали руками или очень давно — на всякий случай сверьте `ip route show | grep
dev antizapret2` на резервном узле после клонирования identity.

## Как срабатывает переключение

Кроме ручных кнопок «Проверить и переключить» / «Сделать активным», панель сама
проверяет здоровье всех пулов с `mode=auto` и стратегией `dnat_front` каждые
**5 минут** (фоновый воркер, переменная `FAILOVER_SCHEDULER_INTERVAL_SECONDS`
в `backend/.env`; полностью выключить — `FAILOVER_SCHEDULER_ENABLED=false`).
Ручные кнопки продолжают работать как раньше независимо от этого воркера —
это два независимых вызова одной и той же функции.

## Приоритет участников

Стрелки ↑/↓ у каждого участника меняют его приоритет местами с соседом. У кого
приоритет `#0` — тот основной (источник identity) и первый кандидат при авто-
переключении. Если пул в режиме `auto` и нужный узел уже здоров, но фоновый
планировщик (см. ниже) постоянно возвращает активным другой — поднимите
нужный узел на `#0` стрелкой, а не только жмите «Сделать активным»: иначе
следующий тик планировщика откатит ручное переключение обратно на более
приоритетный здоровый узел.

## Расформировать фронт

Кнопка **«Расформировать фронт»** в карточке пула снимает DNAT-правило с фронт-узла
и отвязывает его от пула — участники, склонированная identity и привязанные клиенты
не трогаются. Фронт можно назначить заново (тот же узел или другой) в любой момент.

## Проверка вживую

Переключение можно проверить, не трогая клиент: сделайте на пуле «Сделать активным»
для резервного узла, оставьте приложение AmneziaWG подключённым как было, и
посмотрите egress IP через `cdn-cgi/trace` или на странице **Warp Geo** — если IP
сменился без единого действия на клиенте, фронт работает как задуман.

## Мониторинг клиентов по всем узлам

На странице **AZ-AWG2** переключатель **«Все узлы»** тянет список клиентов
(онлайн/офлайн, интерфейс AntiZapret/VPN) со всех VPN-узлов в один список с
фильтрами — не нужно переключать активный узел и листать по одному.
